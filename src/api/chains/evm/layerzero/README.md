# VT wallet execution

`driver.ts` is the dedicated LayerZero build/submit path. Existing Uniswap and LI.FI payloads keep their own execution paths. Backend admission uses the existing app version header (Classic 26.11.2+) and server rollout flag, with no executor capability announcement. Native Air admission remains closed until its native cross-chain flow uses the EVM on-chain build/submit path.

Applications use their unchanged `from`/`to`, addresses, amounts, minimum, fee and provider fields. They do not pass selected-token fields or an estimate handle. SDK `getSwapItemSlug`/`getTokenByAddress` resolves an existing slug or an unambiguous known address; the SDK builds chain-qualified backend IDs. If a bare address names tokens on several chains, the old application call contains no selected chain: VT rejects that unresolved intent instead of guessing from the backend plan. Supporting such a selection requires an explicit contract decision, not hidden access to application state.

`api/common/swapExecutionQuote.ts` keeps the execution budget in a bounded SDK-only cache (100 entries, five minutes). Build matches the complete existing confirmation fields, account and independently resolved assets. If identical displayed quotes have different budgets, the stricter saved ceiling is used, never a higher one. A missing, expired or changed confirmation requires a new estimate. No provider-specific budget, opaque handle or capability field is exposed to applications. The local intent comes from that confirmed request, the SDK token snapshot and account wallets.

`validation.ts` decodes every Wrapper/Delegate/router call against pinned deployments, including exact approvals, destination, minimum, API partner-fee transfer and refunds. It never appends a second wallet fee or accepts quote-supplied targets as an allowlist. Displayed network fee is the route estimate; SDK-held `vtNativeFeeBudget` is a separate signing ceiling bounded by four times that estimate and cannot increase on refresh. Wrapper/Delegate runtime hashes are checked before signing. No frontend fee line or translations are added: the existing application receives the existing amount/fee fields; separate included-fee disclosure would require an application change and is outside this PR.

Only a known single-hop transaction policy is executable: Stargate Taxi, standard OFT V2, CCTP V2. There is no arbitrary signature, calldata patch, delegate installation, arbitrary transport URL or generic provider-call fallback. Approvals use exact amounts. When one is needed, the reset, approval and bridge go as one atomic EIP-7702 account batch, like LI.FI's Permit2 setup; a chain without batch support or a batch above the confirmed fee budget falls back to separate transactions, which wait for receipts and check the resulting allowance. VT has no Permit2 path: its TransferDelegate pulls by ERC20 allowance only. Refresh cannot change the accepted fee/minimum. Pending source receipt never completes a cross-chain swap.

The `layerzeroSwaps` SDK storage journal holds public signed transactions and their local intent. It contains no private key or backend API key. A failed bridge broadcast after signing is reported pending with its hash, not as an error the user could retry into a new swap; resubmitting the same swap rebroadcasts identical bytes. Automatic startup rebroadcast and nonce replacement are not implemented. Cached destination outflow or failed delivery stays pending for protocol recovery; the wallet never sends principal again as a recovery action.

The deployment JSON and wire types correspond to the backend `src/swap/dex/evm/layerzero` snapshot. Update both reviewed manifests together. Full configuration, source links, fee semantics and deployment order are documented in the backend module README. Mainnet quote checks and local fork execution do not prove remote settlement or fee attribution by the VT service.
